G3 simulator implementation plan

Date: 2026-10-14 (Asia/Hong_Kong)
Status: Revised after three independent agent reviews; proposed implementation plan; simulator not implemented

Purpose and authority

G3 is the roadmap milestone simulator correctness, distinct from strategy Stage 3 (position sizing and portfolio RR). Deliver a deterministic five-stage historical simulator whose results match agreed hand calculations, can be replayed, and never use information before it became available.

The README identifies the v3 specification and current parameters as authoritative. Use the transcript reconciliation for supporting evidence. The website roadmap provides milestone context, but can reflect earlier versions. New engineering proposals below require explicit versioning; they are not already confirmed strategy rules.

G3 verifies implementation correctness. Profitability and sample-out-of-sample validation belong to G4; live execution resilience and broker integration belong to later milestones. No live orders are part of this plan.

Current repository and environment

The repository contains specifications, source transcripts/photos, a self-contained website, PDFs, and an assumed RR comparison script with saved data. There is no complete simulator or trading engine. parameters.json explicitly records core_logic_complete=false and unresolved rules.

Python 3.12 is available in the cloud environment. The static website returned HTTP 200, and offline replay reproduced all 20 saved symbol/session RR results and event logs. This validates the existing assumed research model, not the v3 strategy. Do not run the comparison script's network-fetching main() as a simulator: it overwrites tracked results and uses a fixed date inside a rolling data window. PDF regeneration is optional; retained scripts use macOS fonts.

Prerequisites and rule decisions (G1/G2)

Create a versioned decision register with each unresolved item, source evidence, proposed options, chosen answer, strategy-owner confirmation, and hand-calculated acceptance cases. Keep unresolved values visible and reject runs that depend on them rather than filling them silently.

Required decisions include:

  • Minute price field, timestamp meaning, and when a completed observation becomes usable.
  • Renko reference prices, subsequent anchors, B counting, R scope, multiple threshold crossings within one minute, equality, window resets, and dollar versus percentage calculations.
  • Stage 1 historical day convention, price sampling, fluctuation denominator, point-in-time universe and company-action treatment.
  • Candidate ties, shortages, missing-data treatment, and session boundary/half-day behavior.
  • Quantity reference price, nearest-integer ties, and when quantities may be refreshed.
  • Zero-denominator and equal-RR gate actions. Preserve null plus zero_denominator where the portfolio formula is undefined; do not add a smoothing constant.
  • Simulated order timing, fill prices, execution limitations and costs. Distinguish strategy signals from fills.

Start with the confirmed h=1 behavior. Defer h=2/3 until their counting, anchor and reset rules are defined. G2 must supply suitably licensed historical minute data, point-in-time screening inputs and calendars. Synthetic fixtures can support development before these arrive; they cannot establish historical data readiness or complete G2.

Required decisions highlighted by specialist review

Approve a worked causal timeline before coding Stages 4–5: bar start/end, availability time, gate evaluation, initial-price observation, signal, order submission and eligible fill. A bar labelled 10:00 may close at 10:01; its close cannot be used at 10:00. The observation threshold must not use a later Stage 5 initial price. Define event precedence at equal timestamps, including AM liquidation and PM observation at 12:30, and prevent an expired slot from reopening.

Specify session-end execution separately. A next-bar-open model has no regular-session next bar after 16:00. Choose and disclose an idealized exit mark, a supported auction model, or another explicitly approved execution convention. Do not silently move the exit earlier or fill the next day. If data cannot support an executable exit, record the limitation and any residual inventory.

One-minute OHLC does not identify intraminute high/low order. Adopt an approved sampled-price event model for the first release; never silently infer a high-first or low-first path. Specify separately how a multi-threshold jump contributes to B and how many execution actions that observation may generate.

G2 handoff must include documented schemas for minute bars, daily screening values, universe membership and calendars: stable security identifiers, units, interval/availability timestamps, adjustment bases, duplicate/missing-data policy and dataset hashes. A readiness report must verify the selected trade dates, previous scoring session and complete approved screening lookback. Include delisted securities, publication delays, splits and symbol changes where relevant; a supplied frozen universe supports partial testing but not complete Stage 1 acceptance.

Implementation sequence

Step Work Deliverable and exit condition
1. Freeze executable rules Resolve the required decisions above and specify expected answers independently of code. Versioned rule register and strategy-owner-approved fixtures; no unresolved rule used in an accepted run.
2. Replay foundation Validate schemas, timestamps, completeness and company actions; feed observations through a chronological clock that reveals only available information. Data adapters, calendar and deterministic event stream; rejected inputs have explicit reasons.
3. Stages 1–3 Implement screening, independent AM/PM selection using B/(R+1), integer quantities nearest target notional, and portfolio RR ΣB/ΣR. Auditable screening values, rankings, quantities and previous-session baselines matching fixtures.
4. Stages 4–5 Implement whole-list session gating, per-symbol first-event entry, same-direction hold, close-before-reverse and session-end liquidation. Shared strategy state machine plus an explicitly configured simulation adapter; transitions match fixtures.
5. Verification and review Run acceptance tests, multi-session historical replay, repeatability and future-data-leakage checks. Test results, traceable event/fill ledgers and G3 acceptance report reviewed by developer and quantitative reviewer.

Proposed software organization

Use the existing checkout in cloud or a normal local clone; no separate worktree is required. A proposed Python package layout is src/winwin/ with modules for configuration, data/calendar, Renko events, screening/selection, sizing, gates, strategy state, simulation execution, and audit output. Add independently authored fixtures and tests under tests/, and a command-line replay entry point. Dependency choices and a locked installation workflow should be decided during implementation, not inferred from the existing standard-library research script.

The strategy core should accept data events and emit decisions without accessing broker APIs, network calls or UI state. A simulation adapter supplies fills and costs. This separation lets later execution work reuse the strategy rules without assuming simulated fills are attainable live.

Treat the existing parameter document as a specification, not a ready runtime configuration. Build a validated executable configuration from approved decisions; reject unresolved required fields, invalid settings and unsupported modes. Freeze its effective contents at run start and record a canonical hash. Optional proposal values remain disabled unless explicitly selected in a separately labelled configuration.

For the initial acceptance, bound support to h=1, the approved default AM/PM schedule, gate enable/disable, required numeric screening/selection/sizing controls and one approved Renko mode. The eventual dollar/percentage and custom-slot requirements remain in the backlog: each needs its own approved rules and fixtures before it becomes an enabled control. This staging proposal does not change the strategy specification.

Separate data ingestion from offline replay. Resolve runtime paths from an explicit project/data root; the macOS absolute paths in current provenance metadata are descriptive only. Use the same packaged engine, supported Python version, locked dependencies and pinned calendar/timezone policy in cloud and local clones. Test from a working directory outside the checkout. Prefer a Git clone over a loose folder; if copied folders are supported, capture a source-content hash instead of assuming Git metadata exists. Measure resource usage on a small replay before broad-universe runs.

Use explicit decimal precision and rounding for prices/thresholds/cash. Preserve RR numerators and denominators and compare defined ratios by integer cross-products, rather than rounded display values. Define canonical event ordering and output serialization. Each run bundle includes configuration/data hashes, code revision and dirty-state status, execution assumptions, completed/failed status and a completion marker. Interrupted runs cannot appear complete.

Distinguish an idealized fill adapter for signal correctness from an execution-constrained adapter. The initial idealized adapter must state which borrow, buying-power, delay, rejection and partial-fill constraints it does not model. A constrained adapter tracks actual inventory and pending orders; reverse entry depends on confirmed closure, and stale/pending opening intents are handled at slot end. Its extra scope requires data and a separate estimate. Neither adapter silently adds optional strategy risk overlays.

Store immutable input datasets outside source control unless intentionally small fixtures. Write each run to a separate ignored output directory, preserving the existing research files. Record code revision, parameter/rule version, dataset identifiers and hashes, timezone/calendar version, execution assumptions and run status. Do not store credentials in any manifest or log.

Confirmed strategy behavior to preserve

  • Stage 1 uses the four specified screening conditions; do not add optional filters as core rules.
  • Stage 2 has independent previous-day AM 09:30–12:30 and PM 12:30–16:00 candidate lists, with overlap allowed. Individual RR is B/(R+1).
  • Stage 3 chooses positive integer shares nearest the configurable target (default US$1,000). Portfolio RR is summed counts divided by summed reversals, with no +1 or weighting.
  • Stage 4 compares today's AM 09:30–10:00 or PM 12:30–13:00 observation RR against the corresponding previous-day full-slot baseline. Gate decisions apply to the whole candidate list.
  • Stage 5 records initial prices at 10:00/13:00 after gate passage, waits for each symbol's first event, holds on same-direction events without adding shares, and closes before reversing on an opposite event with h=1. Liquidate at 12:30/16:00 even without another Renko event.
  • Strategy times use America/New_York; Hong Kong display times must account for daylight saving. Interval endpoints and special sessions still require explicit decisions.
  • Optional risk overlays and research variants must be separate configurations with visible differences from the faithful core.

Required acceptance cases

  1. No first event means no position; gate passage alone creates no trade.
  2. Same-direction events hold the existing quantity without adding shares.
  3. An opposite event with h=1 requests closure before opening the opposite position; simulated fill ordering is observable.
  4. Session end triggers liquidation without requiring a new Renko event, under the agreed fill model.
  5. Price US335andtargetUS1,000 selects 3 shares worth US1, 005; alsocoverUS900 and US$100 examples and an agreed equal-distance tie.
  6. Portfolio RR uses ΣB/ΣR, not the mean of individual RRs; zero denominator remains explicitly undefined.
  7. Greater/lower/equal RR and unavailable-input gate cases match the agreed policies, including the gate-disabled variant.
  8. AM and PM selection are independent; boundaries cause no unintended double counting and calendar edge cases follow the agreed rules.
  9. Hand-calculated minute paths cover first events, reversals, no movement, exact thresholds and multi-threshold jumps under each supported Renko mode.
  10. Changing observations strictly after time t cannot change decisions produced by t. Availability timestamps, previous-day selection and screening inputs are included in this check.
  11. Identical input data, code, rules and parameters reproduce identical canonical decision/fill outputs; volatile run timestamps are excluded from comparison.
  12. Each signal, order intent, fill and position transition is traceable to its inputs and active version; ledger quantities and cash reconcile.
  13. Equal ratios with different denominators remain equal; exact-threshold and nearest-quantity tie cases obey the approved numerical policy.
  14. Permuting input-file order preserves results; duplicate/out-of-order observations are handled according to the data contract. Same-timestamp exit/signal events cannot reopen expired sessions.
  15. Missing minutes, halts, insufficient warm-up, delayed market-cap publication and splits are surfaced rather than silently filled or ignored. No fill occurs before its order or at an unavailable price.
  16. Invalid or unsupported configurations are blocked. If constrained execution is supported, test rejected shorts, insufficient buying power, delayed/partial closure and cancellation of pending openings at session end; otherwise mark those capabilities unsupported.

Tests must exercise intended cases and report passed, failed, skipped and unrun outcomes separately. Independently calculated fixtures are the correctness oracle; reproducing the old comparison script alone is insufficient.

Provide a documented offline test command and small end-to-end replay command, with a CI correctness gate. Report synthetic rule correctness, historical-data readiness and execution realism separately. Command success does not replace reviewer sign-off, and blocked or skipped required cases prevent full acceptance.

Interface proposal for review

Begin with a reproducible CLI and a saved configuration file. Propose a lightweight local/cloud-accessible review interface once the core is stable: editable versioned parameters, input validation, run controls, five-stage results, a per-symbol timeline and a downloadable audit bundle. The interface must distinguish confirmed rules, unresolved items, experimental choices and execution assumptions. Saving parameters must update the actual engine configuration, not only the displayed values.

The minimum review workflow is: choose a dataset and approved rule version, inspect/validate settings, start a replay, inspect stage outputs and reasons for no trade, then export evidence. Profitability displays, if provided for diagnosis, must clearly identify the fill and cost assumptions and must not imply G4 validation.

The investor review recommends four browser views:

View Required behavior
Prepare Select dataset, dates and rule version; show coverage, supported controls, units, defaults and blocking decisions.
Review settings Show frozen effective configuration and changes from the faithful preset; distinguish approved rules, experiments and fill assumptions.
Inspect results Show five-stage tables and a symbol timeline separating observations, signals, orders, fills and positions; explain every skip or failure.
Compare/export Compare frozen settings and stage outputs; flag dataset/assumption changes; export a reviewable run bundle.

Use explicit statuses such as skipped_by_strategy, flat_no_event, blocked_by_configuration, blocked_by_data, execution_rejected and run_failed. Keep undefined RR distinct from zero. Display dated New York and Hong Kong times with daylight-saving-aware conversion. Show actual gross/net exposure, long/short quantities, turnover, reversals and assumed costs as diagnostics without changing core quantities or adding risk limits.

Operator exercises must demonstrate that changing target notional changes engine quantities while preserving the earlier run; gate failure is distinguishable from gate passage with no first event; undefined/missing inputs are explained; unsupported h/mode choices are blocked; disabling the gate still waits for entry events; and exported evidence traces a complete reversal. Operator acceptance covers this interface separately from numerical core acceptance.

G3 review: programmatic trading feasibility

Date: 2026-10-14 (Asia/Hong_Kong)
Perspective: independent review through a programmatic-trading lens; this is an agent review, not a claim of professional credentials.
Reviewed: implementation plan, README, v3 specification, parameters, transcript reconciliation, and existing comparison script.

Verdict

Proceed with the replay infrastructure and independent fixtures. Do not sign off a faithful historical trading simulation until the rule and execution decisions below are resolved. The five-stage decomposition, explicit unresolved-rule register, causality tests, separation of signals from fills, and deferral of h>1 are appropriate. Most algorithmic work is manageable. The difficult parts are authoritative event definitions, historical point-in-time inputs and attainable execution assumptions, rather than computing RR.

Four development weeks is a plausible planning allowance for a narrowly scoped h=1 simulator after the necessary decisions and usable data arrive. It does not cover obtaining a full historical IB-compatible universe, reconstructing historical short availability, or implementing a realistic broker execution system. Those should be named limitations or separately estimated prerequisites.

Findings and concrete repairs

P0 — Specify a complete causal timeline, especially at 10:00 and 16:00

Confirmed evidence: v3 sections 5–6 require an observation gate, a new Stage 5 initial price at 10:00/13:00, and liquidation at 12:30/16:00. sampling.price_field, sampling.confirmation_time_rule, interval boundaries and execution.fill_simulation_rule remain unresolved. The reconciliation explicitly prohibits using the later Stage 5 initial price to compute the earlier observation's dollar threshold.

Difficulty: a provider's bar labelled 09:59 may cover 09:59–10:00 and become usable at or after 10:00. A bar labelled 10:00 may cover 10:00–10:01. Its closing price cannot be treated as known at 10:00. Similarly, detecting an event from the closing minute and filling it retrospectively at that minute's price creates optimistic execution. A next-bar-open model has no regular-session next bar after 16:00. Merely saying “liquidate at the session end” does not solve this.

Repair: before implementing Stages 4–5, approve a worked timeline specifying bar start, bar end, availability, gate evaluation, initial-price observation, signal creation, order submission and eligible fill time. Add an explicit scheduled-exit policy: an idealized contemporaneous mark for signal correctness, a supported auction model, or a separately labelled execution convention. An earlier exit is a strategy variant, not an invisible fix. Avoid claiming a fill is executable when the dataset lacks the required information.

Acceptance additions: a 10:00-labelled bar cannot influence the 10:00 gate before its data are available; no entry fires from the same observation used solely to establish the new initial anchor; an event coinciding with liquidation cannot reopen the expired slot; the exit model never silently uses a next-day fill.

P0 — One-minute inputs do not reveal intraminute event order

Confirmed evidence: v3 specifies one-minute sampling, but leaves B counting, subsequent anchors, R scope, multiple crossings, threshold equality and percentage compounding unresolved. The old comparison script uses minute closes, carries an anchor by completed dollar increments, and counts multiple crossings. Those are research assumptions, not the executable v3 definition.

Difficulty: OHLC bars do not disclose whether a high occurred before a low. Using them to generate both upward and downward Renko events requires an assumed intraminute path. Minute-close sampling is deterministic but intentionally misses movements between samples. A multi-threshold move also needs two distinct decisions: how many B events exist, and whether one observation can produce several execution actions.

Repair: approve one event-generation contract for the first release. State the sampled price, anchor updates, event count, reversal scope and permitted execution actions per observation. If close-only sampling is chosen, identify it as an agreed sampled-price model. Require finer data for any future intraminute path model rather than inventing a path silently. Use stable decimal/integer arithmetic and explicit rounding rules for thresholds.

Acceptance additions: gaps across three thresholds; first downward event; exact threshold and one increment below it; direction reversal after a gap; unchanged price; dollar and percentage modes; and a sample that would imply different events under high-first versus low-first interpretations. These should prove which interpretation is supported, not compare two implementations of the same assumption.

P0 — Resolve screening as-of time and procure point-in-time inputs

Confirmed evidence: Stage 1 uses 20-day average market capitalization, volume, fluctuation and price, while Stages 2–3 prepare previous-day rankings and quantities. The specification prohibits using later information to establish an earlier universe. The exact IB security scope, day convention and price/fluctuation definitions are unresolved. The comparison script explicitly uses end-of-test-day index weights for a descriptive selection and omits Stage 1 entirely.

Difficulty: current ticker lists and retrospectively revised market-cap series can introduce survivorship and look-ahead bias. Historical market cap may require contemporaneous shares outstanding as well as price; minute prices alone are insufficient. At least 20 eligible historical days plus the scoring day are needed, with the exact overlap dependent on the approved convention. Splits can corrupt thresholds, quantities and counts when daily and minute data have inconsistent adjustment bases.

Repair: define when Stage 1 is evaluated, which completed days enter it, and how late publications/revisions are handled. Require stable security identifiers, valid-date symbol mappings, historical universe snapshots, calendar data and documented adjustment bases. Separate event/effective time from information-availability time. Prefer internally consistent tradable price data and explicitly normalize history for company actions. A frozen supplied universe can support an honest partial replay but cannot count as full Stage 1/G3 historical acceptance.

Acceptance additions: newly listed and delisted securities, ticker changes, a split between scoring and trading days, insufficient warm-up, a market-cap update published after the preparation cutoff, and the distinction between a market holiday and a missing session. Missing minutes or halts must not be silently forward-filled into executable prices.

P1 — Distinguish the signal simulator from executable inventory

Confirmed evidence: v3 section 6 and execution require close-before-reverse, borrow and buying-power checks, and broker reconciliation. They do not provide a fill model or guarantee immediate execution. Additional portfolio risk limits remain disabled proposals.

Difficulty: an opposite signal is not evidence that the prior position has closed. A rejected short, partial close or unavailable quote can leave actual inventory different from the strategy's desired position. Ten US$1,000 allocations also do not establish that the account has adequate buying power. Short-sale restrictions and unavailable borrow can affect trade feasibility without changing the underlying signal rule.

Repair: define two explicit simulation capabilities: a signal-correctness adapter with idealized fills, and an execution-constrained adapter when the necessary inputs exist. Record assumptions and unsupported constraints in the run manifest. In the constrained adapter, track pending orders and actual filled quantities; opening a reversal must depend on confirmation of closure. Specify what happens to stale intents when another signal or a slot-end event arrives. Parameterize account resources and costs without silently adding the optional strategy risk overlays.

Acceptance additions: rejected short entry, insufficient buying power, partial close, delayed close with a newer signal, and slot-end cancellation of pending opening orders. If these are outside the first release, reject configurations claiming those capabilities and label the outputs as idealized execution rather than failing G3 against an unstated broker model.

P1 — Make RR comparisons and exceptional states exact and visible

Confirmed evidence: individual RR is B/(R+1); portfolio RR is sum(B)/sum(R) with no smoothing. Zero portfolio denominator, equal gate values, missing data and ties remain unresolved. The whole candidate basket is gated.

Difficulty: floating-point comparisons can turn mathematically equal ratios into unequal ones. Zero reversals are plausible in a short observation window. Treating an unavailable candidate as a zero count, or dropping it and recomputing the basket, changes the gate. A full previous-day baseline versus a 30-minute current observation is intentional under the present interpretation, but their different horizons make invalid reset/count conventions especially damaging.

Repair: preserve numerator/denominator counts and compare finite ratios by integer cross-products. Distinguish valid, zero_denominator, missing_data and unresolved_rule; do not merge them into numeric zero. Resolve equal-RR and unavailable-basket policies with the strategy owner. Keep the confirmed baseline horizon; a same-30-minute comparison is a labelled research variant.

Acceptance additions: exact equal ratios with different denominators; all B and R zero; B positive with R zero; one missing candidate in the selected basket; duplicate symbols/security identifiers; and deterministic candidate tie handling.

P1 — Add event precedence and operational replay invariants

Confirmed evidence: AM and PM lists are independent and may overlap; both use the 12:30 boundary. Half-days and interval endpoints are unresolved. The plan correctly requests calendar and boundary tests but does not yet give ordering rules.

Repair: define a deterministic priority for data availability, gate decisions, signal processing, fills and scheduled exits at equal timestamps. Define ownership of the 12:30 observation, clear expired slot state, and keep AM inventory separate from PM eligibility. The PM observation starting at 12:30 must not rely on an AM fill or anchor unless the approved rule explicitly requires that dependency. Include daylight-saving transitions, early closes, gaps and halts in the calendar policy.

Acceptance additions: the same symbol appears in both slots; a 12:30 AM event and PM observation coincide; a half-day ends during or before the PM observation; data records arrive out of order or are duplicated. Enforce no fill before its order, no double fill, close-before-reverse, and inventory/cash reconciliation. A session without an attainable exit must surface an unresolved position, not be reported as flat by fiat.

Recommended scope and sign-off

Keep G3 focused on approved one-minute event semantics, h=1, the configured five-stage workflow, deterministic replay and independently checked outputs. Include only execution behavior that the selected adapter and inputs can support. Require separate evidence for synthetic rule correctness, historical data readiness and fill realism; success in one does not establish the others.

Before sign-off, the strategy owner should approve the causal timeline and rule register, the quantitative reviewer should independently calculate adversarial fixtures, and the developer should produce the replay/audit evidence. Historical results should disclose input coverage, rejected/skipped sessions, execution assumptions and residual positions. Profitability remains G4, and live broker integration remains later work.

G3 engineering review

Date: 2026-10-14 (Asia/Hong_Kong)
Perspective: Experienced software engineering review; an independent review perspective, not a claim of professional credentials.
Reviewed: G3 plan, README, v3 specification, parameters, and research comparison script. This is a static architecture and repository review, not simulator execution or performance validation.

Verdict

The simulator is feasible in this repository and in a normal local clone. The plan has the right core structure: an offline, deterministic strategy engine, separate simulation execution, independent expected answers and versioned evidence. Building a narrow h=1 simulator is moderately challenging; the largest uncertainty is incomplete strategy and data contracts, rather than Python implementation.

Approve the implementation direction subject to the repairs below. Four development weeks is plausible for a CLI, synthetic fixtures, one historical data adapter and bounded historical acceptance after prerequisites are resolved. It is not a reliable estimate for data procurement, all configurable strategy variants, broker integration or a polished interactive interface.

Findings and required repairs

1. Define the executable configuration contract before implementing stages — high priority

The parameters file mixes confirmed rules, provenance, unresolved null fields and explicitly disabled optional proposals. It is not yet an executable configuration schema. A generic loader could accidentally enable proposal values, accept incomplete rules, or interpret descriptive strings as algorithms.

Repair: introduce a validated runtime configuration derived from the authoritative specification and approved decision register. Explicitly allow supported rule versions and modes; reject unresolved required fields, unknown options, invalid ranges and unsupported h>1 values. Validate custom slot ordering, observation-before-monitor timing and calendar compatibility. Preserve the existing source specification; write resolved runtime configurations as separate versioned artifacts. Freeze a copy for each run so editing a file during replay cannot alter decisions. Acceptance must include invalid configurations and prove optional proposals remain disabled.

2. Specify event order and order lifecycle — high priority

The plan correctly requires close-before-reverse, availability timestamps and session-end liquidation. However, a chronological clock alone does not decide what happens when a minute completes, a gate opens, a symbol generates an event and a session ends at the same timestamp. AM liquidation and PM observation both involve 12:30. Different iteration orders can produce different positions even with identical data.

Repair: define a deterministic ordering key, for example availability time plus an approved event-type priority, symbol identifier and sequence number. Keep bar interval time separate from observation availability time. Define whether boundary events are processed before liquidation and how the 10:00/13:00 anchor is obtained without reading a still-incomplete bar. Add boundary fixtures with multiple symbols and permuted input file order. Give order intents and fills explicit identifiers and states; a reversal opening must depend on the closure being filled under the configured adapter. A narrow immediate-fill adapter is acceptable initially if documented, but it must not silently claim coverage of delayed, partial or rejected fills.

3. Make data readiness inspectable and replay independent of fetching — high priority

The existing script couples fetching with calculation, assumes 390 regular-session minutes, uses only ten fixed symbols and overwrites result files. Its saved single-day data cannot demonstrate Stage 1's 20-day screen and previous-day-to-current-day workflow. The plan recognizes this, but needs a concrete interface between G2 and G3.

Repair: define separate ingestion and replay commands, with replay working offline. Specify the minute-bar, daily-screening, universe-membership and calendar schemas, including timezone, availability time, adjustment basis, units, identifiers, duplicate policy and missing-data policy. Require a readiness report identifying the chosen trade dates, prior session and complete screening lookback, including point-in-time market-cap inputs. Use the small saved dataset only as a research regression fixture with its assumptions clearly labeled. Do not promise full historical acceptance until the readiness report passes.

4. Fix portability at the loader boundary — medium priority

The parameters file contains provenance paths under /Users/macmini001/Desktop/Win-win/. These do not exist in cloud or most other local folders. The research script uses zoneinfo; installed Python alone does not ensure that every host has suitable timezone data. The README also records macOS-only font paths in PDF tooling.

Repair: treat absolute provenance paths as descriptive metadata, never as runtime input locations. Resolve actual inputs relative to an explicit project/data root, or through command-line paths. Keep PDF tooling outside mandatory simulator dependencies. Document a supported Python version, install into a project virtual environment, lock dependencies, and provide a repeatable calendar/timezone-data policy. Test from a fresh clone and from a working directory other than the repository root. Repository location must not affect canonical results.

5. Specify numerical and audit contracts — medium priority

Threshold equality, closest-integer sizing and RR gate comparisons are sensitive to floating-point rounding. Recording a parameter version label is insufficient if the contents change while retaining that label. Mutable output files also make repeatability difficult to establish.

Repair: choose one explicit decimal precision/rounding policy for prices, thresholds and cash. Compare count-based RR ratios exactly where practical, after handling zero denominators, rather than rounding displayed ratios before gate decisions. Include dataset hashes, canonical configuration hash, approved rule identifier, calendar version and code revision; record whether uncommitted implementation changes were present. Use unique run directories and a final completion marker so interrupted runs cannot appear successful. Define canonical ledger ordering and exclude wall-clock timestamps only from the comparison representation, not from provenance records.

6. Turn acceptance ownership into an executable release gate — medium priority

The proposed acceptance cases are strong. They need a runnable contract that differentiates a synthetic correctness pass from a historical-data pass, and prevents the developer from silently changing expected outputs to match the implementation.

Repair: independently review expected fixture values before writing stage code; link each fixture to a rule decision. Add negative-input tests, same-time event ordering, decimal equality, unavailable close prices and output ledger reconciliation. Provide one documented test command and a small offline end-to-end smoke command. Produce an acceptance matrix with passed, failed, skipped and blocked cases; record reviewer sign-off separately from command success. A basic CI check should run the offline suite on future changes. Avoid duplicating every implementation branch with tests that simply restate the code.

G3 review: investor usability and flexibility

Date: 2026-10-14 (Asia/Hong_Kong)
Perspective: investor/operator review; this is an analytical review, not a claim of professional credentials.
Reviewed proposal: G3 simulator plan

Verdict

Proceed with G3, subject to a small, explicit operator interface and the unresolved-rule decisions already required by the plan. The proposed separation of strategy, replay, fills and audit records is suitable for reviewing this strategy. A CLI and JSON file are a useful engineering baseline, but are insufficient as the final comfortable workflow for an investor expected to change settings, understand a skipped session and compare runs.

The engine can support a practical research workflow without live brokerage integration. G3 should prove that approved rules execute correctly and can be understood. It does not establish profitability, suitable account sizing, or readiness to place live orders.

Basis for the review

  • The README identifies v3 and current parameters as authoritative and describes the repository as research/specifications, not an execution system.
  • v3 sections 2–7 require editable stage settings, independent AM/PM lists, the configurable trade gate and distinct k and h controls. Section 7 explicitly requires changes to reach the engine and every stage output.
  • parameters.json lists intended editable fields, unresolved rules and disabled optional overlays. It also records that the interface is not implemented and core logic is incomplete.
  • v3 sections 5, 6 and 8 distinguish a gate passing from an entry, signals from attainable fills, and optional overlays from the faithful core.

Minimum practical interface

Use a lightweight browser review interface backed by the same CLI/replay engine. It should work in a local browser and through the cloud environment's supported preview connection. Keep saved configuration, run bundles and results portable between those environments. The interface framework can be chosen by the implementation team; no complex frontend is required for G3.

  1. Prepare run. Select immutable dataset, dates and approved rule version. Start with a faithful v3 preset. Show data coverage, missing prerequisites and supported settings before execution. Group controls by the five stages, show units, validate ranges and session relationships, and offer reset-to-version defaults. Explain that target notional may be slightly exceeded by nearest-integer sizing.
  2. Review settings. Show the full effective configuration and changes from the preset. Keep confirmed rules, approved decisions, experimental variants and execution assumptions visibly distinct. Unsupported choices should identify the exact unresolved rule instead of falling back silently. A disabled gate still waits for the first entry event.
  3. Run and inspect. Show progress and passed/failed/blocked status. Present a five-stage summary: screening counts and rejection values; independent AM/PM rankings; quantities and rounding differences; baseline/current portfolio counts and gate outcome; event/order/fill transitions and final positions. Opening a symbol reveals its timestamped price/event/position timeline, including data-availability times and separate signal/fill prices.
  4. Compare and export. Choose two completed runs for a configuration and output diff. Download configuration, input identifiers/hashes, stage tables, ledgers, validation results and a readable summary. A saved run should remain reviewable without restarting the simulator.

For the first G3 release, correctness/reason tables and export matter more than animated charts or a P&L dashboard. If P&L is shown for ledger reconciliation, label its fill/cost assumptions and keep it separate from a strategy-performance claim.

Operator acceptance exercises

These supplement the numerical and causal acceptance cases in the implementation plan; they do not replace them.

  • Change target notional, save a new version, run a sizing fixture and verify that both the effective settings and quantities changed. The previous run must remain unchanged.
  • Inspect a session whose gate failed and a session whose gate passed but had no first events. The operator should be able to explain why neither traded without reading source code.
  • Supply missing data and a zero-denominator case. The interface should display the precise input/rule issue, preserve null RR and distinguish rejection from a successful empty trading session.
  • Compare gate-enabled and gate-disabled runs using the same dataset and execution settings. Show the gate difference and which entry decisions changed; disabling the gate must not create immediate positions.
  • Attempt h=2 while its reset rule is unresolved. Execution should be blocked with a clear reason, rather than producing an apparently accepted result.
  • Inspect an AM/PM boundary and a US daylight-saving date. Exchange times, Hong Kong dates, observation periods and liquidation times should agree with the accepted calendar rules.
  • Export a run bundle and use it to trace a reversal from inputs to signal, close fill, reverse fill and reconciled final holdings.

Scope and schedule recommendation

Keep the four-week estimate for the correctness engine conditional on rule/data readiness. The plan currently places a review interface after the core becomes stable; therefore do not assume a polished browser interface is already included in that estimate. Budget the minimal interface explicitly or add it as a follow-on usability milestone. Configuration capture, reason codes and portable bundles belong in the engine from the start, so a later interface does not require redesign.

Defer parameter-search automation, custom portfolio weights, unsupported h/mode/session variants, sophisticated visualizations, multi-user accounts, live feeds and broker order controls. Their future addition should preserve the faithful v3 preset, versioned alternatives and auditable run history. G4 can evaluate performance and robustness once G3 is accepted.

Recommended plan amendments

Make operator sign-off an explicit G3 review item; define the no-trade/status vocabulary; capture immutable effective settings at run start; add exposure/cost diagnostics without changing core strategy; and state whether the minimal browser interface is inside or after the four-week engine estimate. These changes make the existing design more usable without expanding G3 into a live trading product.
